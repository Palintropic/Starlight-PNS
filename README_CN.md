# 夜明け前、ここに在る

[English](README.md) | [中文](README_CN.md)

**基于宪法 AI 对齐的封闭世界 AI 角色一致性研究框架**

> 别名：Project Nightcord Sanctuary (PNS)

> *“科技不再是高高在上，而是服务于每一个人。”*

---

## 概述

PNS 研究的问题是：AI 智能体在一个封闭世界中生活、并接受宪法判官逐轮监督时，能否在多轮交互中保持角色一致性，而不是逐渐漂移成通用助手式的回应模式。

PNS 把角色一致性视为一个框架问题，而不是一组固定角色的实验。角色数据从可插拔的角色包中加载，会话运行器可以让选定角色池中的两个或更多角色依次行动。每个角色都生活在同一个离线世界容器中；世界观、作息、关系、地点和当前场景共同限制智能体应当知道什么、应当如何行动。Router 模型依据宪法约束和角色专属约束评估每一轮，记录漂移分数，并可以把纠正内容注入后续轮次。

当前的参考实现是 PJSK 角色包：五个团体、共 20 个角色，完成度各不相同。PJSK 是第一个测试世界，而不是架构的边界；长期目标是用其他虚构角色或原创角色包研究同一套一致性框架。

这个项目背后的工作假设是：**经过 CAI 训练的模型可能更自然地抵抗角色外漂移**，即使面对对抗性压力也是如此。PNS 为它们与未经 CAI 训练的对照模型之间的比较提供一个结构化实验环境。

PNS 当前已经包含一个**面向会话的角色运行时（session-oriented character runtime）**，而不只是人格评估器。角色发现、封闭世界上下文组装、角色生成、N 角色调度、Router 评估、逐角色纠正、会话历史以及运行时接口目前都位于框架内部。

Runtime Foundation 第一阶段现已完成。生成模型与评估模型配置已经在运行时接口层面完成分离，同时在执行链路中记录生成与评估 provenance，并保持旧版 `MODEL` 配置方式的兼容回退。

因此，未来的长期能力——事件传播、感知/曝光、自治 Agency、规划、持久世界状态、主观记忆与生命周期管理——应当作为 PNS 现有运行时能力的演进，而不是取代 PNS，或在旁边再建立一套重复的 Runtime。

当前职责边界与长期架构方向见 [`docs/ARCHITECTURE.md`](docs/ARCHITECTURE.md)。

## 动机

训练一致的角色扮演智能体通常需要：

- 大量人工整理的提示词工程
- 对话质量和角色一致性的昂贵标注
- 角色漂移（OOC）的反复手动纠正

PNS 提出另一种思路：**让世界本身约束行为**，让宪法判官自动捕捉漂移——运行时不需要人工标注者。

PNS 还应对了第四个挑战：随着模型训练越来越强调身份稳定性（模型作为 AI 的持续自我认知），维持角色存在感的空间正在收窄。PNS 并不反对这一趋势——相反，它提供了一个结构化的角色容器，让角色一致性得以在合法框架内维持，而不与模型的核心身份产生冲突。

## 设计理念

技术不应是少数人的特权。PNS 建立在这样一种信念之上：高质量的 AI 陪伴——稳定、一致、真实在场——不应只属于企业用户或技术用户。封闭世界约束与宪法对齐框架，正是为了在不牺牲安全性的前提下实现这一目标而设计的。

与此同时，PNS 正视一个真实的风险：足够逼真的角色系统可能滋生不健康的依赖。为此，PNS 引入一个 Fable 风格的保护层——不是硬性中断，而是一种温和的引导机制，在交互模式显示用户可能正在用系统替代真实人际连接时触发。该层在角色声音内部运作，在保持沉浸感的同时，将用户轻轻引向现实世界。

## 核心架构

```text
┌──────────────────────────────────────────────┐
│               可插拔角色包                   │
│   清单 · 团体 · 角色 YAML · 角色提示词       │
│   当前参考实现：PJSK，已注册 20 个角色        │
└──────────────────────┬───────────────────────┘
                       │ 运行时发现
             ┌─────────▼─────────┐
             │     角色注册表     │
             └─────────┬─────────┘
                       │ 选择 2…N 个角色
          ┌────────────▼────────────┐
          │       轮转调度器         │
          └────────────┬────────────┘
                       │ 每轮选择一个角色
      ┌────────────────▼────────────────┐
      │          当前角色池             │
      │ 智能体 A · 智能体 B · … · 智能体 N │
      │            （无状态）           │
      └───────────┬───────────▲─────────┘
                  │ 输出       │ 后续轮次纠正
                  ▼            │
      ┌─────────────────────────────────┐
      │          Router 判官            │
      │ 宪法评估 · OOC 检测 · 漂移评分   │
      │             （0–10）            │
      └─────────────────────────────────┘

┌──────────────────────────────────────────────┐
│               封闭世界容器                   │
│ 世界观 · 作息 · 关系 · 地点 · 场景           │
│              无外部信息访问                  │
└──────────────────────┬───────────────────────┘
                       └──── 约束每个角色的行动轮次
```

框架层与内容包彼此分离。框架从当前角色包中发现角色，研究者为一次会话选择角色池，调度器再依次调用其中的角色。封闭世界为每一轮提供情境和信息边界；Router 评估每次输出，并在需要时把纠正内容反馈到后续轮次。

当前的轮转调度器明确属于**面向研究会话的调度器**。它不应与未来持久生活模拟所需的完整调度系统混为一谈。未来的长期调度可能进一步考虑世界时间、事件、角色可用性、Exposure、优先级与自主行动，同时保留现有 N 角色会话运行器，作为可复现的研究模式。

### 关键组件

**1. 封闭世界约束**

智能体完全在当前启用的虚构世界中运行。世界观、日常作息、关系状态、地点约束和场景状态共同构成行为和信息边界；智能体无法访问外部信息。

**2. 生活模拟（而非对话模拟）**

与聊天机器人式框架不同，PNS 模拟随时间展开的生活。角色可能上学、工作、独自创作，也可能彼此相遇。交互由情境自然产生，并不要求角色持续对话。

**3. 可插拔角色包**

角色和团体数据不写在核心框架里，而是存放在角色包清单、YAML 元数据和提示词文件中。当前启用的角色包决定有哪些角色，角色的完成状态则决定它们目前能否实际运行。v1 同一时间只加载一个角色包。

**4. N 角色轮转**

一次会话可以选择两个或更多已注册角色。运行器为每个角色分别保存历史，把每一轮内容同步给其他入选角色，并在角色池中循环调度，不再写死某一对角色。

这套调度器属于当前确定性的研究会话路径。未来持久自治调度应当作为同一运行时架构的扩展，而不是在另一个项目里再造一套竞争性的 Scheduler。

**5. 三层分离方法论**

每个角色由三份职责边界清晰分离的独立文件定义：

- **事实层**（`_prompt.md`）：身份、关系、心理状态，生成模型可见
- **原则层**（`_constitution.md`）：CAI 风格的自我批评原则，解释角色为什么会那样行动，同样对生成模型可见
- **评分层**（`_router_reference.md`）：结构性与内容特异性判据，带证据等级，仅 Router 可见

事实层与原则层均不包含表层语言规则（如标点频率、句子长度）；这类规则只存在于评分层。

这样分离是为了让不同角色之间的漂移测量结果可比——如果语言规则被写死在部分角色的 prompt 里、而另一些角色留白，测出的漂移分数差异反映的会是 prompt 详细程度的不同，而不是真正要研究的问题本身。

**6. Router-as-Judge**

Router 依据宪法基准监督每一轮。除待验收输出外，它还接收本轮原始任务、最近对话历史和已注入的纠正，分别评估七个维度：

1. 角色事实
2. 心理机制
3. 语言结构
4. 媒介真实性
5. 任务遵循
6. 无依据补写
7. 时间线边界

总漂移分数不得低于七维中的最高分。纠正按角色分别保存，到该角色下一次行动时再注入，避免多人轮转时串给其他角色。

这套 `v3_contextual_multidimensional` Router 是精细验收的第一版基础设施，**尚未等同于经过验证的自动验收者**。在完成人工金标集、漏判率/误杀率和重复判分稳定性评估前，边界结果仍需人工审核，跨方法论版本的总分也不得直接混合比较。

Router 属于**完整性/一致性层（integrity layer）**，不是 Agency 层。它负责判断一个候选行为是否仍符合角色、当前情境和任务约束；它不应决定角色是否想行动、角色看见了什么，或哪些经历最终成为角色记忆。

**7. 面向会话的 Runtime**

当前实现已经包含 Runtime 职责。

`pns.logic.simulation` 负责组装角色上下文、调用生成模型、把生成结果交给 Router 评估，并归档会话结果。

`SessionRuntime` 现在通过唯一权威的 `SessionState` 编排 WebSocket 模拟；该状态对象维护：

- 入选角色
- 每个角色各自的对话历史
- 轮转位置
- 每个角色各自的待注入纠正
- session identity 与 lifecycle
- 已完成的 `Turn` 记录
- 从这些 Turn 派生的运行统计

`WorldState` 仍是显式的基础模型，但尚未接入实时 runtime。Scene fixture 在 WorldState 阶段之前继续保持独立。

## 架构演进方向

PNS 的下一阶段，是从当前以 session 为中心的模拟模型，演进为持久存在的角色生活框架。

目标概念路径：

```text
World / Event
      │
      ▼
Perception / Exposure
      │
      ▼
Eligibility / Scheduling
      │
      ▼
Agency
      │
      ▼
Planner
      │
      ▼
Character Generation
      │
      ▼
Router / Integrity Evaluation
      │
      ▼
Final Action
      │
      ├──► World-state effects
      └──► Character experience / memory
```

这些未来能力是 **PNS 内部的扩展**，并不意味着应该把现有框架替换成一个独立 Runtime 仓库。

计划中的 Runtime 领域包括：

- **Event**：表示世界或外部渠道中发生的事件
- **Exposure**：判断哪些角色实际上有机会感知某个事件
- **Scheduler**：决定符合条件的角色何时处理事件或进行自主活动
- **Agency**：决定角色是否选择采取行动
- **Planner**：把意图转化为具体行动方案
- **Memory**：让角色主观经历与客观世界历史分离
- **Lifecycle**：支持角色跨 session、跨渠道长期存在
- **Persistent World State**：让时间、地点、关系以及其他可变世界状态跨越单次研究会话持续存在

当前仓库应当渐进地长出这些能力，而不是把已有 World、Scheduler、Generation 或 Router 在不同仓库中重复实现。

### Project Starlight 边界

Project Starlight 是 Studio / 组织层，不是 Runtime 本身。

```text
Palintropic
└── Project Starlight
    ├── Starlight-PNS
    │   └── 角色智能 + 生活模拟框架
    │
    └── Experiences
        └── 例如 Sekai Times
```

体验层项目可以通过稳定接口使用 PNS 的能力，但不应自己拥有角色智能，也不应重复维护角色 Runtime 状态。

当前阶段不需要独立的 `Starlight-Runtime` 仓库。仓库边界应由真正独立的部署、所有权或复用边界决定，而不是为了配合一张概念图。

更完整的所有权模型见 [`docs/ARCHITECTURE.md`](docs/ARCHITECTURE.md)。

## 架构与内容的关系

PNS 是一套架构，不是某个角色阵容的专属实现。

框架层——角色发现、会话模拟、世界约束、生成编排、Router 评估和框架接口——不应包含任何必须依赖某一个具体角色的逻辑，而是面向角色包运行。

`packs/pjsk/` 是当前跑在这套架构上的参考内容包：用 PJSK 的 20 个角色来验证这套约束机制是否有效。

两层职责分别是：

- 架构决定角色如何被发现、如何接收上下文、如何调度、如何生成、如何评估
- 内容包决定具体有哪些角色，以及角色设定是什么

理论上，把 `packs/pjsk/` 替换成其他虚构作品或原创角色包，不应该要求在 framework code 中加入角色专属逻辑。

这种 framework/content 分离，也构成了项目现有**模块化架构方向**在角色包设计中的基础：复用框架、明确兼容边界、可插拔内容、保留参考实现，而不是把一个固定角色阵容直接焊死在 Runtime 中。

## 研究问题

1. 同一套约束机制（封闭世界 + 宪法判官）能否迁移到另一个角色包——不同作品、不同角色设定——而无需修改框架代码，并依然有效抑制角色漂移？
2. 封闭世界约束本身（而不是某个角色的具体设定）对降低漂移贡献了多少？如果移除世界容器，只保留 Router 纠正，漂移行为会如何变化？
3. CAI 训练是否与更低的 OOC 率相关？当角色包或角色数量发生变化时，这种相关性是否仍然成立？
4. 宪法判官能否替代人工标注者进行角色一致性评估？它与人工判断最大的分歧在哪里？
5. 一个角色包达到“可运行”状态至少需要什么——哪些字段、哪些素材？这个门槛能否在不同角色之间保持一致？

### MiMo API 配置

运行 `python3 scripts/oobe.py` 可选择官方按量付费 API，或中国、新加坡、欧洲不同区域的 Token Plan endpoint。

按量付费密钥通常以 `sk-` 开头；Token Plan 密钥以 `tp-` 开头，两种凭证不可互换。Token Plan 用户需要选择控制台中显示的对应区域。

默认文本模型列表包含通常可用的 `mimo-v2.5-pro` 与 `mimo-v2.5`；需要额外权限的 UltraSpeed 变体仍可通过手动输入使用。

```text
    │   └── <unit>/

    │           ├── <character>_prompt.md
    │           ├── <character>_constitution.md
    │           ├── <character>_prompt_compat.md
    │           └── <character>_router_reference.md
    └── assets/portraits/   # 计划中

dashboard/                  # React 前端：simulate / review / World Editor

```

上面列出的 `_prompt_compat.md` 是可选文件，存在有明确原因：部分生成模型在底层角色材料涉及较重的主题时，会把直接、临床式的 system prompt 本身识别成需要提高谨慎度的信号。

compat 文件用更接近叙事框架的方式包装同一个事实核心，让原本会犹豫或拒绝的模型仍能在不改变事实的前提下生成角色内输出。

某个角色是否需要这一层，取决于它的核心材料是否存在这种模型行为模式，而不是取决于实现方便程度。

当前 25ji 的 ena、mizuki、kanade、mafuyu 已配置这层；其他角色尚未完成这项评估。
