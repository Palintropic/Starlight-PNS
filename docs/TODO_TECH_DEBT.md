## data/drift_scores.jsonl 的 methodology_version 标注

**状态更新（2026-08-13）**：新运行记录现在由服务端自动写入
`"methodology_version": "v3_contextual_multidimensional"`，并附带七维评分、原始直接要求和
本轮实际应用的纠正。下述内容仅用于解释v1/v2存量数据，不能与v3分数直接混合比较。

**背景**：v2 重构（三层分离方法论落地，`kickoff/Kanade/pns_v2_upgrade_spec.md` 任务6）前后，
`router.py` 判分所依据的机制不同——重构前 `ROUTER_SYSTEM` 里混杂着按角色硬编码的判断规则，
重构后（commit `3984c5d`，2026-08-10 22:26:55）改为运行时动态加载各角色的
`{character}_router_reference.md`。两套机制测出的 drift_score 不是同一把尺子，不应直接
混合比较。

**判定方法**：以 `3984c5d`（router.py 动态加载重构落地）为分界点，交叉核对两个独立信号——
记录的 `timestamp` 是否早于该提交时间，以及记录里是否存在 `router_reference_status` 字段
（这个字段是重构的同一个提交里才加进 `scripts/server.py` 的 drift_record，重构前的代码根本
不会写这个 key，不是"值为空"而是"key 不存在"）。两个信号一致时才判定版本，不一致则标
`unknown`，不强行归类。

**当前结果**：现存 10 条记录（全部来自 2026-08-09 21:07–21:08，`mizuki`/`ena` 各5条）时间戳
和缺失 `router_reference_status` 字段两个信号完全吻合，均判定为 `v1_prescriptive`；无
`v2_layered` 或 `unknown` 记录（重构后至今还没有新跑过会话）。每条记录已加上
`"methodology_version": "v1_prescriptive"` 字段。旧版当时不会自动写入该字段；这一缺口
现已在v3调用链中补齐，后续新记录会同时带上 `router_reference_status` 与
`methodology_version`。

```
- 对绘名的情绪变化很敏感，会顺势引导（解读对方，但只在她允许时才介入）

- 直接给出建议或解决方案（助手化偏移）

- 追问延伸具体而非抽象：从一个具体点随口延到相邻具体点（"刺绣→那衣服呢"），不问"你还有什么特长"这类抽象问题

重点：
- 情绪靠句子本身的节奏体现，不靠拟声词堆砌
- 判断标准是"密度和情绪浓度是否匹配"，不是"句子是否够短"
- 长句子不一定OOC，只要情绪浓度足够撑得住就可以
```

## Exposure（P6）刻意留下的口子

**位置**：`pns/runtime/exposure/`、`pns/models/exposure.py`、`pns/models/observation.py`

P6 只建立"这个角色能不能感知到这条已提交事件"这一层。下面几条是明确知道、明确不在
本阶段修的，列在这里以免被当成疏漏：

- **`event.participants` 在 channel / location 档里语义重载**。P5 的
  `dialogue_event_for_turn` 会把提交那一刻在场/在频道里的人写进 `participants`。那是有价值的
  历史事实，但它跟 `private`/`participant` 档里"被点名的人"是两种含义。曝光层已经按档区分对待
  （只有后两档认这个字段），所以当前没有泄漏路径；但一个字段承担两种含义早晚会被误用。
  后续阶段应当二选一：要么改名成 `present_at_commit` 之类的独立字段，要么在 channel/location
  档里不再填它。

- **"离开"感知不到**。`character.location_changed` 只有一个落点（目的地），所以到达能被目的地
  的人感知，离开不能被原地的人感知。补它需要一条独立的离开事件，属于事件模型的活，不是曝光
  规则能偷偷补的。

- **静音（mute）没有建模**。频道在场只有"是不是成员"一档。静音被判定为注意力/通知层的概念
  而不是感知资格：静音频道里的消息你去看还是看得见的。等 Attention 层出现时再处理。

- **公开事件没有事后发现路径**。`public_not_perceived` 表示"当下没撞上"，不表示永远看不到。
  feed / 时间线发现机制属于后续阶段；在它出现之前，公开事件对不在场的人就是没发生过。

- **可用性没有自然演化**。`Availability` 只能被外部显式设置，世界时钟推进不会让谁睡着或醒来。
  作息表属于 `AgentState` / Scheduler，不在这一层。

- **`SessionState.record_turn(turn)` 不传观察时仍是全知扇出**。这是留给不经过世界模型的纯记录
  调用方的兼容路径，运行时不走它（`tests/test_session_runtime.py` 里有一条测试盯着这一点）。
  等最后一批遗留调用方迁完，这条分支应当直接删掉。

- **观察还不是记忆**。`SessionState.observations` 是完整的感知流，没有衰减、没有编码、没有
  取回。角色记忆是独立的下游数据产品，不能直接拿这条日志当记忆用。

- **遗留场景开场白仍然发给所有会话角色**。`SessionState.initialize_runtime()` 把
  `【场景】<trigger>` 塞进每个角色的历史，不经过曝光。它是遗留 fixture 的叙事开场，不是已提交
  事件，所以 P6 没有动它；但它确实是一份"选进会话就自动共享"的知识。等开场改由结构化观察
  和可用动作生成时，这条应当一起消失。

## 配置重载（P7）刻意留下的口子

**位置**：`pns/runtime/content_registry.py`、`pns/runtime/reload.py`、`pns/interfaces/config.py`

P7 只做「停下来、整体重建、原子替换、失败回滚」这一层。下面几条是明确知道、明确不在
本阶段修的：

- **停止不是抢占，所以慢会话会把重载拖失败**。`request_stop()` 只打标记，会话在下一个轮次
  开始前才观察到。重载会等到所有旧会话确认退出才切换（这是"新旧配置不并存"的落实点），
  但如果某一轮卡在一次很慢的模型调用上，等待就可能撞上 `stop_timeout`，整次重载失败。
  要让最坏情况可控，得给生成调用加超时和取消——那是生成层的活，不在这一层。

- **失败的重载留下一批"已被通知停止"的会话**。等待超时时那些会话已经收到停止信号了，
  它们仍然会在各自的轮次边界退出。也就是说一次失败的重载不是完全无副作用的：配置没变，
  但正在跑的会话确实被中断了。

- **`.env` 里的 API Key 不进快照**。`ModelSettings` 只记住变量名，用的时候现从 `os.environ` 取。
  所以改 Key 之后不重载也会立刻生效，跟其他配置的"重载才生效"语义不一致。这是为了不让密钥
  在内存里到处复制，属于有意为之，但确实是个语义缺口。

- **`pns/world/scenes.py` / `facts.py` 仍然是 `.py`**。它们现在走 `pns/world/data_module.py` 的
  严格 AST 白名单求值（不执行代码），但文件后缀和位置还在假装自己是模块，`codegen` 也还得
  用 black 生成 Python 源码。真正该做的是把它们挪成 YAML/JSON 放到数据目录里，那时
  `data_module.py` 和 `codegen.py` 都可以整个删掉。

- **白名单是按当前两个数据文件的需要定的**。它认字面量、dict/list/tuple/set、负号，以及引用
  本文件里更早定义过的名字。以后数据文件真需要别的表达能力时，加节点必须重新想一遍安全性，
  不能顺手放开——这个求值器的输入来自一个没有鉴权的写接口。

- **`SCENE_WORLD_MAP` 是 cold update**。World Editor 能造出新场景，但新场景需要一条写在 Python
  源码里的世界映射，所以"能存进磁盘、存完不生效"是可达状态（接口会明说）。等场景不再需要
  手写映射（位置由场景直接声明 location_id）之后这条消失。

- **遗留缓存还在**。`pns/world/characters/registry.py` 的 `_cache` 和 `pns/world/__init__.py` 里
  import 时求值的 `SCENES`/`WORLD_FACTS` 仍然存在，服务于还没迁到 ContentRegistry 的调用方
  （`pns.world.get_character_system` 等）。运行时不走它们，但它们会跟重载后的配置不一致。
  等最后一批调用方迁完应当直接删掉。

- **重载不做鉴权**。`POST /api/config/reload` 会停掉所有正在跑的会话，而整个 API 层目前没有
  任何鉴权（见 `docs/API.md` §6）。部署到本机之外之前必须先补鉴权。

- **没有配置历史**。保存失败会把文件原子恢复成保存前的内容，所以"重启起不来"这个状态不会
  由保存操作造成；但人直接编辑磁盘上的文件仍然可以把它改坏，重载/重启都救不回来。
  World Editor 的 `.bak` 是单份覆盖式备份，不是版本链——回滚用的是事务开始时读到的字节，
  跟 `.bak` 无关。

- **事务只覆盖单个进程**。`write_and_reload()` 记的是自己读到的那份字节，靠进程内的重载互斥锁
  跟别的保存/重载排他。如果同时有别的进程或人在改同一个文件，回滚会把对方的改动一起盖掉。
  当前部署是单进程本机服务，先按这个前提走；真要多进程就得上文件锁。

- **保存会被正在进行的重载挡回去**。共用一把互斥锁的代价：一次重载最长可能占用
  `stop_timeout` 那么久，这期间所有保存都返回 409。对单人用的本机后台够了，多人用要排队
  就得另想。
