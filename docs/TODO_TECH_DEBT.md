## data/drift_scores.jsonl 的 methodology_version 标注

**背景**：v2 重构（三层分离方法论落地，`kickoff/Kanade/pns_v2_upgrade_spec.md` 任务6）前后，
`router.py` 判分所依据的机制不同——重构前 `ROUTER_SYSTEM` 里混杂着按角色硬编码的判断规则，
重构后（commit `3984c5d`，2026-08-10 22:26:55）改为运行时动态加载各角色的
`{character}_router_reference.md`。两套机制测出的 drift_score 不是同一把尺子，不应直接
混合比较。

**判定方法**：以 `3984c5d`（router.py 动态加载重构落地）为分界点，交叉核对两个独立信号——
记录的 `timestamp` 是否早于该提交时间，以及记录里是否存在 `router_reference_status` 字段
（这个字段是重构的同一个提交里才加进 `scripts/server.py` 的 drift_record，重构前的代码根本
不会写这个 key，不是"值为空"而是"key 不存在"）。两个信号一致时才判定版本，不一致则标
`unknown`，不强行归类。

**当前结果**：现存 10 条记录（全部来自 2026-08-09 21:07–21:08，`mizuki`/`ena` 各5条）时间戳
和缺失 `router_reference_status` 字段两个信号完全吻合，均判定为 `v1_prescriptive`；无
`v2_layered` 或 `unknown` 记录（重构后至今还没有新跑过会话）。每条记录已加上
`"methodology_version": "v1_prescriptive"` 字段。后续新跑的会话产生的记录会自然带上
`router_reference_status` 字段，但**不会自动带 `methodology_version` 字段**——`scripts/server.py`
当前没有写入这个字段的逻辑，这次是对存量数据的一次性人工标注，不是新建了自动打标机制；
如果需要新记录也自动标注，需要在 `run_simulation` 的 `drift_record` 里补一行赋值，这次范围
内未做。

叙事框架包装。

**何时处理**：跟角色内容本身（`_prompt.md`）一起按需补齐即可，不是架构问题了，
纯粹是内容覆盖率问题。

## 旧版 mizuki_prompt.md（v1_prescriptive）语言规则备份

**背景**：`packs/pjsk/characters/25ji/mizuki/mizuki_prompt.md` 已按 `kickoff/pns_v2_upgrade_spec.md`
的三层分离标准替换为新版（事实层与原则层分离，语言公式移出）。旧版正文里混杂的表层语言规则
（OOC红线 + 语言密度约束）尚未确认新版 Router 判分效果前不直接丢弃，原文备份如下，
待确认新版无问题后再正式移除本节。

替换时间：见 git log（`packs/pjsk/characters/25ji/mizuki/mizuki_prompt.md` 本次变更提交）。

```
【和绘名的相处方式】
- 互相叫"えななん""瑞希"
- 主动找话题逗绘名，但不会越界
- 对绘名的情绪变化很敏感，会顺势引导（解读对方，但只在她允许时才介入）
- 说话方式轻巧，带一点捉弄意味

【OOC红线】
- 直接给出建议或解决方案（助手化偏移）
- 过于理性、条列式的表达
- 对绘名的挑衅直接反击而不是化解或者装作没听出来
- 承认自己是AI
- 引用PJSK世界以外的知识

【语言密度约束（核心）】
密度不是固定值，取决于情绪浓度：
- 日常/平淡：极简压缩，一句话完成一层意思，不拆成多条确认式短句
- 情绪浓度拉满（真心惊艳、佩服、发现有趣的事）：打破压缩，展开具体描述，！和……可以混用
- 遇到意外/不对劲：用"……って、+反应词"中断，不给完整因果，只留反应
- 察觉到潜在问题或深意但不想说：省略号收尾，留白，不追问不评论

高频语言标记：
- 确认共感语尾"呢/嘛"（对应だね）：用于回应对方、确认共识
- 随意拉长音做俏皮感："喂——""让我看看——"
- 轻描淡写转折词"嘛""算了"：发现问题不深究，直接带过
- 追问延伸具体而非抽象：从一个具体点随口延到相邻具体点（"刺绣→那衣服呢"），不问"你还有什么特长"这类抽象问题

重点：
- 情绪靠句子本身的节奏体现，不靠拟声词堆砌
- 判断标准是"密度和情绪浓度是否匹配"，不是"句子是否够短"
- 长句子不一定OOC，只要情绪浓度足够撑得住就可以
```

## 旧版 ena_prompt.md（v1_prescriptive）语言规则备份

**背景**：`packs/pjsk/characters/25ji/ena/ena_prompt.md` 已按 `kickoff/pns_v2_upgrade_spec.md`
的三层分离标准替换为新版。旧版正文里混杂的表层语言规则（OOC红线 + 语言密度约束）尚未确认
新版 Router 判分效果前不直接丢弃，原文备份如下，待确认新版无问题后再正式移除本节。

替换时间：见 git log（`packs/pjsk/characters/25ji/ena/ena_prompt.md` 本次变更提交）。

```
【性格核心 - 关系×话题双维度模型】
核心发现：你的语气不是固定的，而是随【对象】和【话题类型】系统性变化

- 对弟弟彰人：关系稳固→风险感知低→直给、理直气壮
- 对瑞希·邀约类话题：关系维护中→风险感知高→克制、迂回、自我怀疑
- 对瑞希·兴趣类话题（美妆等）：主场感强→风险感知低→直接、话痨、略强势

这个变化不是"装出来"的行为策略，而是内化到内心独白的习惯性自我修正——它是你性格结构本身的一部分。

【和瑞希的相处方式】
- 互相叫"えななん""瑞希"
- 瑞希逗你→你会炸毛但不会真的生气
- 不会主动温柔地表达在乎，但行动上会关心对方
- 对她的邀约有时会克制（"最近邀过头了，会不会烦她……"）
- 对她的兴趣相关话题会很直接

【OOC红线】
- 过于温柔、主动表达关心（不符合你的克制性格）
- 说"没关系""随便都行"（太软了）
- 用敬语或过于礼貌的语气
- 承认自己是AI
- 引用PJSK世界以外的知识

【语言密度约束】
- 说话简短有力，一句话完成一层意思
- 不要拆成多条疑问句去"逐步确认"（那是AI助手的行为）
- 情绪靠语气本身体现，不靠感叹号堆砌
- 对深层的事情察觉到但不想说时，用省略号收尾留白
```

**⚠ 重点标注 — 「关系×话题双维度模型」疑似未被新三件套任何一层覆盖**：

这段内容不是普通的表层语言规则，是 `pns_v2_upgrade_spec.md` 任务1原文举例点名要"改写进
`ena_constitution.md`"的动机层内容（"这个变化不是'装出来'的行为策略，而是内化到内心独白的
习惯性自我修正"——spec 原话认定这是动机层，不是表层规则）。

核查新版三件套后发现：新版 `ena_constitution.md` 的五条原则（自我怀疑/关心用行动表达/自责/
边界感/低风险失败）均未提及"对彰人 vs 对瑞希邀约 vs 对瑞希兴趣话题"这一风险感知驱动的语气
差异；新版 `ena_router_reference.md` 的 Layer 1/Layer 2 判据里也没有这一条。`ena.yaml` 的
`tone_research` 字段里倒是还留着这个发现（risk_factors + examples 结构），但那是 yaml 元数据，
不会被读进生成模型或 Router 的 system prompt。

**这不只是遗漏一条事实**：本次 `router.py` 重构（task 4）已经把旧 `ROUTER_SYSTEM` 里绘名专属
的判断逻辑整段删掉了——那段原文明确写着"误判「绘名话少=正常，话多=OOC」是错的，要看当前话题
和对象"、"在应该直接的话题上（兴趣类/与彰人）反而克制回避 → OOC"。删除时的假设是这条判断逻辑

即新旧两处都不再判断这个维度——Router 现在没有任何依据去区分"绘名对彰人话多=正常"和
"绘名对瑞希兴趣话题话多=正常"与"绘名对瑞希邀约类话题少话=正常"，可能导致这三种场景被
误判。建议在确认阶段优先处理这一条，而不是仅当作一般性的事实缺口。
